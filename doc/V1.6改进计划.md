## 1. 背景与目标

V1.5 已定稿（`v1.5.0`）。本版本新增一个**关于界面**，用于展示应用自身的身份信息：
APP 名称、版本号、版权信息。

三类典型用途决定了它不是一个「可有可无」的页面：

1. **作品集场景**：本项目定位是个人作品/作品集（SRS 1.2），评审者或协作者拿到 APK 后，
   第一件想知道的事就是「这是什么、哪个版本、谁做的」。
2. **问题反馈**：真机返工时最常缺的信息是版本号（V1.5 一轮返工就吃过这个亏 —— 当时无法
   确认设备上装的是哪一版，只能靠 `versionCode` 逐版递增来区分）。
3. **归属声明**：版权信息是作品的归属标识。

### 1.1 与既有需求的关系

SRS 5.1 的界面清单目前有：主菜单、启动图标、关卡选择、游戏主界面、暂停弹窗、结算弹窗、
设置界面 —— **没有关于界面**。因此本版本是一次**需求新增**，需同步 SRS（见 §6.1）。

## 3. 设计约束

| # | 约束 | 来源 |
|---|---|---|
| 1 | **不新增任何权限**，尤其不得为了「检查更新」引入网络权限 | SRS NFR-6.1 / NFR-6.3 / AC-20；FR-12.4「不含 BGM」同源的约束思路 |
| 2 | **不新增第三方依赖** | 本版本只是展示静态信息，无此必要（也符合「依赖清单定稿」的基线） |
| 3 | 关于界面**必须透明覆盖在动态背景之上**，不得画不透明满屏底色 | V1.5 计划 §15.1（两屏 `Scaffold` 默认底色把背景整层盖住的事故） |
| 4 | 版本号**必须来自构建产物**，不得在界面代码里写死 | 否则改版本号时必然漏改一处 |
| 5 | 文案一律走 `strings.xml`，不在 Compose 里写死中文字面量 | 既有约定（M6 起全部文案资源化） |
| 6 | 文本对比度沿用主题角色（`onSurface` / `onSurfaceVariant`），不引入自定义颜色 | `ThemePaletteContrastTest` 已对 4 套配色逐对断言 WCAG 对比度 |
| 7 | 分层不变：`domain/` 不得 import `android.*` / `androidx.*` | SRS NFR-3.1（每个里程碑都复核） |
| 8 | 必须支持系统返回键与顶部返回按钮 | 与关卡选择、设置界面一致 |

## 4. 技术方案

### 4.1 版本号从哪来（本版本唯一有技术含量的决策）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 打开 `buildFeatures { buildConfig = true }`，读 `BuildConfig.VERSION_NAME` / `VERSION_CODE` | 编译期常量；无 API 弃用问题；`BuildConfig.DEBUG` 顺带可用于区分构建类型；纯 JVM 单测可直接断言 | 需要改一处构建配置（一行） |
| B | `PackageManager.getPackageInfo(packageName, 0)` | 不改构建配置；反映**已安装 APK**的真实版本 | API 33+ 该重载被弃用，需按版本分支；需要 `Context`，单测里无法直接覆盖 |
| C | 在 `res/values/` 里放一个手写的 `version_name` 字符串 | 最简单 | **违反约束 4**，直接排除 |

取 **A**。理由：本项目的版本号唯一真源是 `app/build.gradle.kts`，`BuildConfig` 正是它的投影；
`versionName` 与 `versionCode` 同时展示还能顺带解决「设备上装的是哪一版」这个 V1.5 遇到过的问题。

### 4.2 展示内容与排版

```
┌─────────────────────────────┐
│ ← 关于                       │  TopAppBar（透明，复用既有样式）
├─────────────────────────────┤
│                             │
│         [ 应用图标 ]          │  自适应图标的前景层（矢量，任意尺寸不糊）
│          连连看               │  R.string.app_name（与桌面图标同名）
│       版本 1.6（构建 12）      │  BuildConfig.VERSION_NAME / VERSION_CODE
│                             │
│   一句话简介（可选，Q2）        │
│                             │
│  ─────────────────────────  │  HorizontalDivider
│   版权行（Q3 给定文字）         │
│   技术栈/致谢（可选，Q2）       │
└─────────────────────────────┘
```

- 文字全部使用主题角色：名称 `headlineSmall` + `onSurface`，版本 `bodyMedium` + `onSurfaceVariant`，
  版权 `bodySmall` + `onSurfaceVariant`。
- 图标用 `painterResource(R.drawable.ic_launcher_foreground)`（V1.4 生成的自适应图标前景层，
  已按 66dp 安全区作画，因此任何尺寸都不裁切）—— 不额外生成资源。

## 13. 待确认项（实施前需要开发者决定）

### Q1 「关于」的入口放在哪？

- **A（推荐）**：**设置界面底部**（「清除进度」下方）。
  与 M3 习惯一致；主菜单按钮数不变（4 个），既有验收观感不受影响；入口位置唯一，不产生两个维护点。
- B：**主菜单底部**。更显眼，适合作品集展示；代价是主菜单从 4 个按钮变 5 个。
- C：**两处都放**。最容易被找到；代价是两处入口都要维护，且主菜单仍会变。

### Q2 关于界面显示到什么程度？

- **A（推荐）**：应用图标 + 名称 + **版本（名称 + 构建号，如「1.6（构建 12）」）** + 一句话简介 + 版权行。
  简介用现有定位拟一句（例：「经典连连看：两张同图案的牌用不超过 2 个拐点的折线相连即可消除」）。
- B：最小集 —— 名称 + 版本 + 版权行（不要图标、不要简介）。
- C：在 A 之上再加**技术栈与致谢**（Kotlin / Jetpack Compose / Material 3，以及所用开源库一行致谢）。
- D：在 A（或 C）之上再加**设备与构建信息**（Android 版本、机型、debug/release），便于反馈问题时附带。

### Q3 版权行的确切文字是？（**必须由你给定，我不能臆造**）

- A：「© 2026 leid」（取仓库提交者署名）
- B：「© 2026 连连看」
- C：其它 —— 请直接给我完整一行文字（是否含年份、是否用 `©`、是否加「保留所有权利」等）

> 附带一问：年份要**写死**还是**运行时取当前年**？
> 写死：文字稳定、可预期，但跨年后需要手动改；
> 运行时取：永不落后，但同一份 APK 在不同年份显示不同（对作品集而言通常想要「发布年份」）。
> **默认取写死**（推荐）。

### Q4 是否显示联系方式？

- **A（推荐）**：不显示。最简，且不涉及个人信息暴露。
- B：显示邮箱（取自仓库提交者 `ld-1@163.com`，或另给一个）。
- C：显示一个可点击链接（如作品集/仓库地址；用 `ACTION_VIEW` 交给浏览器，**不需要新权限**）。
