## 3. 设计约束（核心）

**这是益智游戏：玩家需要持续扫视棋盘找配对。动态背景最大的风险不是性能，而是干扰玩法。**

以下约束是硬性的，会写成代码里的常量并由测试断言：

| 约束 | 取值 | 理由 |
|---|---|---|
| 运动周期 | **≥ 20 s** | 周期太短会形成「节律」，吸引注意力 |
| 元素透明度 | **≤ 0.08** | 背景元素必须弱到「看久了才注意到」 |
| 元素数量 | **≤ 8 个** | 控制绘制预算，也控制视觉噪声 |
| 形状 | **不得为圆角方形，也不得使用皮肤图案** | 避免与真实牌混淆 —— 这是本版本最容易出的错 |
| 可用颜色 | **仅中性色**（`background`/`surfaceVariant`/`outline` 一类） | **不得使用 `primary`/`tertiary`/`error`** —— 它们分别承载选中、提示、错误语义，背景若用同色会抢注意力、甚至造成误判 |

最后一条尤其重要：V1.3 定下的三个强调色各有明确语义（选中/提示/错误），
背景若从中取色，会直接削弱这三个信号的辨识度。

**关于棋盘的隔离**：牌目前直接浮在背景上。若背景开始运动，牌与背景的边界会变得不稳定。
**建议给棋盘加一层极淡的底板**（scrim），既能隔离运动背景、又能提升牌的对比度。
但它会改变 V1.4 刚验收过的棋盘观感，因此列为待确认项（§13 Q2）。

## 4. 技术方案

新增 `ui/theme/AnimatedBackground.kt`：

```kotlin
/** 动态背景的全部参数，纯数据 —— 便于断言 §3 的约束。 */
data class BackgroundSpec(
    val blobCount: Int,
    val alpha: Double,
    val periodMillis: Int,
    val colors: List<Color>,
)

@Composable
fun AnimatedBackground(modifier: Modifier = Modifier)
```

实现要点：

1. **用 `Canvas` 的 draw lambda 读动画状态，而不是在组合期读**。
   `Canvas` 底层是 `drawBehind`；在它的 draw block 里读 `State<Float>` 只会让**绘制阶段**失效，
   **不触发重组**。若在组合期读，每帧都会重组一遍整棵子树 —— 这是本项目首次引入常驻动画，
   这点做错代价很大。
2. **参数集中为 [BackgroundSpec]**，形如「N 个柔和圆形，各自按不同相位/速度缓慢漂移」。
   圆形用 `Brush.radialGradient` 画（边缘自然淡出，不需要模糊）。
3. **不要每帧分配对象**。`Brush.radialGradient` 每帧新建会有 GC 压力；
   尽量把不随帧变化的量提到 draw 之外，或用 `drawWithCache` 缓存。
4. 只有 `modifier` 与 `spec` 是入参，颜色由当前 `MaterialTheme.colorScheme` 推导 ——
   因此 4 套主题色下背景自动协调。

## 5. 性能与省电

应用此前无常驻动画，因此需要主动约束：

| 措施 | 说明 |
|---|---|
| **仅在 RESUMED 时运行** | 用 `LocalLifecycleOwner` + `repeatOnLifecycle(RESUMED)` 驱动；暂停/后台时停掉动画。否则锁屏或切后台仍在空耗电量 |
| 绘制预算 | ≤ 8 个径向渐变圆 + 1 个基底渐变。**不引入模糊、不引入位图、不做全屏逐像素计算** |
| 不参与布局 | 背景用 `drawBehind`/`Canvas` 绘制，不影响测量与布局 |
| 与棋盘动画共存 | 棋盘上同时可能出现连线/消除/抖动三种动画。背景必须是最轻的那个 —— 真机验收要专门看消除动画期间是否掉帧 |

**无法在编码侧测量帧率**（本机无模拟器），因此 §9 的真机验收里有一项专测流畅度。

## 6. 尊重系统的「减少动效」

Android 通过 `Settings.Global.ANIMATOR_DURATION_SCALE` 表达「移除动画」偏好
（无障碍设置里的「移除动画」以及部分省电模式会置 0）。

建议：读取该值，为 0 时**渲染静态版本**（即当前的渐变），不做任何运动。

这是一条低成本、高价值的无障碍处理 —— 而且比新增一个应用内开关更符合用户预期
（用户已经在系统层面表达过偏好，不该再让他进设置里关一次）。

待确认项 §13 Q3。

### 14.1 实际取值

| 参数 | §3 硬约束 | 实际取值 |
|---|---|---|
| 数量 | ≤ 8 | **5** |
| 单个光斑透明度 | ≤ 0.08 | **0.055**（约上限的 2/3，给真机调参留余量） |
| 周期 | ≥ 20 s | **30 s**（三路速度另取 ×1.31、×1.73，逐路都 ≥ 30 s） |
| 半径 | —— | **屏幕短边的 0.35 ~ 0.70** |
| 用色 | 仅中性色 | `surfaceVariant` / `outlineVariant` / `onSurfaceVariant` |

### 14.2 与计划的差异

| 项 | 计划 | 实装 | 原因 |
|---|---|---|---|
| §4 的 `BackgroundSpec` 字段 | `blobCount` / `alpha` / `periodMillis` / `colors` | `blobCount` / `maxAlpha` / `periodMillis` / `radiusRange` | ① 颜色必须由当前 `ColorScheme` 推导（4 套主题色下都要成立），塞进常量对象里反而会诱使调用方写死色值；② `alpha` 拆成「上限 `maxAlpha`」与「每个光斑的实际取值」，是为了让「单个光斑 ≤ 0.08」这条约束在**运行时**也能被断言；③ 半径区间是 §3 之外的补充约束，写进 spec 才能被单测覆盖 |
| §5 的生命周期门控 | 「用 `repeatOnLifecycle(RESUMED)` 驱动」 | `LifecycleResumeEffect` + **把动画组合整段移出组合树** | `InfiniteTransition` 没有「暂停」API，只有在非 RESUMED 时让承载它的 composable 离开组合，才能真的取消其协程与帧请求（而不是「每帧画一个不动的位置」这种假停）。`LifecycleResumeEffect` 就是 `repeatOnLifecycle(RESUMED)` 的 composable 形式 |
| §4 第 3 条（避免每帧分配） | 「尽量把不随帧变化的量提到 draw 之外，或用 `drawWithCache` 缓存」 | 画笔缓存 + **画布平移** | 光斑的半径/颜色/透明度都不随帧变化，只有位置在变；把位置交给 `withTransform { translate(...) }`，每个光斑的 `Brush` 就能整帧复用 —— 稳态下每帧零 `Brush` 分配（`Offset`/`Color` 是 JVM 值类，本身不产生堆分配） |

**Q2（不加棋盘底板）的连带影响**：§9 的 **V-7 作废**，代码里没有任何棋盘侧改动；牌继续直接浮在背景上。

**Q3（不读系统「减少动效」）的连带影响**：**§6 整节未实施**，**A-3 与 V-6 作废**；
代码里不存在 `ANIMATOR_DURATION_SCALE` 判定，测试里也没有相关用例
（留一个永远通过的测试反而会让人以为该功能已实现）。取舍已记入 README 的「已知取舍」表。
`AnimatedBackground.kt` 里的 `StaticBackground` 分支正是日后恢复该功能所需的落点。

### 14.3 计划未覆盖、实施时做的两个决定

1. **非前台时背景退化成 V1.4 的那层静态渐变**（而不是「冻结在最后一帧的光斑」）。
   应用不在前台时人看不到它，没必要为「看起来连续」多维护一份冻结逻辑。
   副作用：再次回到前台时相位从 0 重新开始，光斑位置会跳一次 —— 透明度只有 0.055 上下、
   移动极慢，预计看不出；**列入 V-5 的真机观察项**。若要消除，需额外记录相位基准（约十行）。
2. **每帧的绘制调用固定在 6 次以内**（1 次基底 `drawRect` + 5 次光斑 `drawCircle`），
   无模糊、无位图、无逐像素运算（§5 的绘制预算）。

### 14.4 仍需真机验收的项

## 15. 修订 1：真机反馈「完全看不出背景在动」（2026-09-14）

§14 的实现在真机上被判定为**功能未达成**：开发者在四个界面（主菜单、关卡选择、设置、
游戏界面）都看不出背景有任何变化。以下记录排查、结论与改法。

### 15.1 排查结论：两个**互相独立**的原因，各自都足以让背景看起来完全没变

| # | 原因 | 证据 |
|---|---|---|
| **A** | **两层界面把背景整层盖住了。** `LevelSelectScreen` 与 `SettingsScreen` 用了 `Scaffold`，而 `Scaffold` 的默认 `containerColor` 是 `colorScheme.background` —— 一个**不透明**的满屏 `Surface`。这两屏因此完全没有背景（连 V1.4 的静态渐变也一直被盖着，只是没人注意过）。主菜单与游戏界面没有 `Scaffold`，不受此影响 | 源码：两处 `Scaffold` 均未传 `containerColor`；`MenuScreen` / `GameScreen` 无 `Scaffold`、无 `background` |
| **B** | **光斑在数学上就看不见。** 像素差 = 透明度 ×（底色 − 光斑色）。初版光斑取 `surfaceVariant` / `outlineVariant`，与底色 `#F8F9FC` 的差只有 29 / 57 级，乘上 0.033~0.055 的透明度后**峰值像素差只有 1~2 级（约 0.5%）**，远低于人眼在大面积色块上的察觉阈值 | 复算（4 套主题色 × 逐光斑）：`0.96 / 2.51 / 10.12 / 0.96 / 2.51` 级 |

> **B 是本版本最值得记住的一条**：§3 把约束立在**配方**上（「透明度 ≤ 0.08」），
> 而真正决定成败的是**成品**（合成后的像素差）。初版 6 条单测全绿，测的全是配方 ——
> 配方合法、成品不可见。详见 §15.4。

排查时还顺手排除了两个假设：① 应用确实装的是 V1.5 包（开发者自建安装）；
② 生命周期门控没有把动画卡在静止分支（`LifecycleResumeEffect` 在已 RESUMED 时会立即派发
`ON_RESUME`，`isResumed` 会被置真）。

### 15.2 第三处改动：不再依赖「画布变换是否作用于画笔着色器」

初版把画笔圆心固定在原点、再用 `withTransform { translate(...) }` 把画布挪到光斑位置，
好处是画笔可跨帧复用（§14.2 记为「稳态下每帧零 Brush 分配」）。

代价是它依赖一条**本机无法验证**的平台行为：画布变换是否同样作用于渐变着色器。
本机是虚拟化环境、起不了模拟器，唯一能证实它的办法是渲染出来看 —— 而这正是做不到的事。
（按 Skia 与 Android 的通行语义，变换是作用于着色器的，初版大概率没有错；
但「大概率」不足以作为一次真机返工的理由。）

因此本版改为**按光斑实际圆心创建画笔**（`Brush.radialGradient` 的 `center` 与
`drawCircle` 的 `center` 传同一个值），代价是每帧新建 4 个短命画笔，收益是这条依赖归零。
§14.2 关于「每帧零分配」的那一行随之作废，改为「每帧 ≤ 4 个小对象」。

### 15.3 视觉构想改为参照开发者的既有实现

开发者提供了参照效果：`Birthday` 项目的 `app/src/main/java/com/example/birthday/ui/components/FloatingOrbs.kt`
（三个半透明光球**缓缓上浮**并左右摆动，透明度另有一层更快的「呼吸」）。
本版据此重做形态与节奏。

**两处必须偏离参照实现的地方**（都源于两个项目的底色相反）：

| 项 | 参照实现（Birthday） | 本实现（连连看） | 原因 |
|---|---|---|---|
| 明暗关系 | 底色是饱和深紫—品红渐变（`#3D1D6E`→`#7B2FBE`→`#D81B60`），光斑用**白色**（比底色亮） | 底色是近乎白的浅色渐变（`#F8F9FC`），光斑只能用**比底色暗**的中性色 | 比近白更亮的颜色不存在。观感因此是「淡雾上浮」而非「白色光球」，这是浅色主题下的必然结果 |
| 透明度 | 峰值 0.16（白色 × 深底） | 峰值 0.10（中性色 × 浅底） | 「看得见」取决于合成后的像素差。参照实现在深底上的像素差约 20~31 级，本实现在浅底上取 12.6~20.3 级，量级相当 |

若日后想要参照实现那种「白色光球」的原味观感，前提是底色改成饱和或深色的渐变 ——
那会与 V1.3 的「4 套浅色主题色、无深色模式」决策冲突，不是本版本能顺手做的事。

### 15.4 修订后的取值

| 参数 | 修订前 | 修订后 | 依据 |
|---|---|---|---|
| 形态 | 5 个大光斑沿椭圆轨迹漂移 | **4 个光斑从屏幕下缘之外升到上缘之外**，横向摆动 2 圈 | 参照实现；上浮的起止点都在屏幕之外，因此循环处天然无缝（修订前靠 sin/cos 保证连续） |
| 数量 | 5 | **4** | 参照实现是 3 个 |
| 峰值透明度 | 0.055 | **0.10**（上限 0.12） | 由像素差反推，见下 |
| 用色 | `surfaceVariant` / `outlineVariant` / `onSurfaceVariant` | **`onSurfaceVariant` / `onSurface`** | 两者都是中性角色（不是语义色），且与底色的差为 184~226 级，乘上透明度后落在可见区间 |
| 上浮周期 | 30 s（三路 ×1.31 / ×1.73） | **20 s（四路 ×1.0 / ×1.25 / ×0.85 / ×1.45 = 17~29 s）** | 参照实现是 10/12/14 s，本项目放慢但仍明显在动；下限从 20 s 放宽到 15 s 并逐路断言 |

**`每个光斑的峰值像素差 ∈ [11, 28] 级（0~255）、周期 ≥ 15 s、数量 3~8`**。
即把约束从「配方」改到「成品指标」上，配方数字只是它的副产品。

### 15.5 测试相应重写：从「测配方」改为「测成品」

每个光斑在其呼吸峰值处都看得见

级，4 个光斑低于门槛）—— 这正是它存在的意义：把「配方合法但成品看不见」这类事故变成红灯。

另新增「呼吸不会让光斑完全消失」一条；「透明度不超上限」一条保留，但降级为配方检查，
并在注释里写明它不是可见性的保证。

## 16. 修订 2：真机反馈「每个界面都没看到动态背景」（2026-09-14）

> ⚠️ **本节的结论已被 §17 推翻，请先读 §17。** 本节把「系统动画程序时长缩放为 0」
> 认定为根因，但开发者随后确认该设备上的值**并非 0**，因此这个机制虽然真实存在
> （库源码可证），**却不是本次「看不到」的原因**。本节保留，是因为其中的排查方法、
> 被排除的假设、以及「自己数帧 + 错开初始相位 + 门控只冻结时间」这三处改动仍然有效。

§15 的修订 1 之后，真机反馈变为**每个界面都看不到动态背景**（主菜单、关卡选择、设置、
游戏界面）。这次与配色无关 —— **动画根本没有推进**。

### 16.1 根因：系统的「动画程序时长缩放」为 0 时，Compose 会把进度直接取到动画结尾

Compose 的 recomposer 会从**系统设置**里读「动画程序时长缩放」（Animator duration scale）
并装成一个 `MotionDurationScale` 参与上下文的：

```kotlin
// androidx.compose.ui.platform.WindowRecomposer.android.kt
Settings.Global.getFloat(contentResolver, Settings.Global.ANIMATOR_DURATION_SCALE, 1f)
```

而动画在逐帧推进时，会把「已播放时长」按这个缩放系数折算，**缩放为 0 时走的是特殊分支**：

```kotlin
// androidx.compose.animation.core —— SuspendAnimation.doAnimationFrameWithScale
val playTimeNanos =
    if (durationScale == 0f) {
        anim.durationNanos          // ← 直接取到动画结尾
    } else {
        ((frameTimeNanos - startTimeNanos) / durationScale).toLong()
    }
```

于是 `animateFloat(initialValue = 0f, targetValue = 1f, ...)` 的值**恒为终值 1.0**，
`infiniteRepeatable` 每帧都「立刻跑完」再重开。代入修订 1 的纵向位置公式：

```
centerY = 屏高 × (RISE_START − RISE_TRAVEL × phase) = 屏高 × (1.15 − 1.45 × 1.0) = −0.30 × 屏高
```

四个光斑**全部停在屏幕上方之外**，屏幕上自然什么都没有 —— 与「每个界面都看不到」完全吻合。

**同一根因也解释了修订 0**：进度恒为 1.0 时，`sin`/`cos` 算出的位置与进度 0 完全相同
（周期函数），光斑静止地停在屏内；而修订 0 的像素差只有 1~2 级（§15.1 的原因 B），
所以同样看不见。**两轮返工，一个根因。**

### 16.2 被排除的假设（都查过，不是猜的）

| 假设 | 结论 | 依据 |
|---|---|---|
| 前台门控（`isResumed`）一直是 false，于是走了「只画渐变」的分支 | **排除** | `LifecycleRegistry.addObserver` 在注册时会把新观察者**补发**到当前状态（源码里那段 `while (statefulObserver.state < targetState) dispatchEvent(upFrom(...))`），所以已 RESUMED 时订阅也能收到 `ON_RESUME` |
| 光斑被上层不透明底色盖住 | **排除**（修订 1 已修） | 主菜单与游戏界面没有 `Scaffold`；关卡选择与设置的 `Scaffold` 已在修订 1 改为透明底色 |
| 光斑画出来了但太淡 | **无法排除，因此一并加强** | 修订 1 的动画压根没跑，「够不够显眼」这个问题在两轮反馈里都没有得到验证 —— 所以 §16.3 把浓度取到偏浓的一端 |

> **教训**：两轮返工都是**用一个纯函数就能验证的量**（像素差、进度）没有被验证，
> 而验证不了的量（渲染效果）被当成了验证对象。所以修订 2 的第一步不是改代码，而是**去读
> 库的源码**，把「Compose 到底怎么算这个进度」这件事从「无法验证的猜测」变成「可以引用的一行代码」。

### 16.3 改法

| # | 改动 | 为什么 |
|---|---|---|
| 1 | **自己用 `withFrameNanos` 累计帧间隔来推进进度**，删掉 `rememberInfiniteTransition` / `infiniteRepeatable` / `tween` | 原始帧回调**不经过**动画时长缩放，系统把缩放设成多少都影响不到它。这是本次的核心修复 |
| 2 | **四个光斑的初始相位互相错开**（0 / 0.42 / 0.71 / 0.17） | 原先都从 0 开始，于是「时间不推进」和「功能不存在」在现象上无法区分（都停在屏幕外）。错开之后，最坏情况是「看得见但不动」——可诊断 |
| 3 | **前台门控只决定时间是否推进**，不再决定画什么（`StaticBackground` 分支删除） | 让门控判断错误的最坏结果是「画面静止」而不是「整层背景消失」。这直接对应第二轮返工时无从下手的处境 |
| 4 | 门控改为手写观察者 + **初值取自 `lifecycle.currentState`** | 不依赖「框架补发 `ON_RESUME`」这一行为（虽然它确实成立，见 §16.2），读者不必再去确认一次 |
| 5 | 峰值透明度 0.10 → **0.13**（上限 0.15） | 「够不够显眼」尚未被真机验证过。修订 2 刻意取到**偏浓**的一端先确认「看得见」，确认后回落到 0.10~0.11 只需改这一个数 |
| 6 | 补一条**时钟断言**：`进度按上浮周期循环 - 且初始相位互相错开` | 把「时钟」这件事从 Composable 与系统设置的交互里挪到纯函数上，让它能被单测钉住（这正是前两轮缺的那一块） |

**一个顺带的、好的副作用**：累计的是帧间隔而不是绝对时间，所以应用切到后台（平台不再派发帧）
时进度自然停住、回到前台接着走 —— 修订 1 的「回到前台相位从 0 重开、光斑位置跳一次」
（V-5 的观察项）随之消失。

**另一个必须说明的副作用**：修复之后，背景动画**不再受系统「动画程序时长缩放」影响**，
把它设成 0 也照样运动。这与计划 §13 Q3 = B（不读系统偏好）是一致的，属于既定决策的自然结果。

### 16.4 ⚠️ 由此发现的一件事：该设备上本 APP 的其它动画很可能也一直是「瞬变」

`MotionDurationScale` 是**全局**的：只要系统把「动画程序时长缩放」设为 0，本项目里
所有基于 Compose 动画的过渡都会退化成瞬间完成 —— 包括牌位移动画（洗牌滑动）、
消除动画（缩放 + 淡出）、错误抖动、按压回弹、提示条进出。这些都属于此前各版本
真机验收里「动画是否流畅」的部分。

**建议**：在完成 V1.5 验收前，先确认设备的
**设置 → 开发者选项 → 动画程序时长缩放**（部分机型在无障碍里叫「移除动画」）是否为 0。
若为 0，请改回 1x 后重新过一遍 **M11 与 V1.1~V1.4 里和动画有关的验收项**（至少：
消除动画、洗牌滑动、错误抖动、提示条），确认那些验收结论在动画真正跑起来时依然成立。
本项目的代码侧不受影响 —— 这是测试环境的问题，不是代码的问题。

### 16.5 仍需真机确认（取代 §15.6）

## 17. 修订 3：绘制、位置、时钟都正常，问题只是**浓度**

> **本节关于「看不见」的结论仍然有效，但用色已被 §18 修订**：`primary` / `tertiary` 主题色
> 取代了这里的中性灰。§17.4 那两条教训（像素差是必要条件而非充分条件；氛围型参数只能靠
> 真机 A/B）依旧成立 —— §18 甚至又给它加了一条：**「可见」与「好看」是两件事**。

### 17.1 先把自己上一节的结论降级（重要）

§16 把「系统动画程序时长缩放为 0」认定为根因。**该结论对本设备是错的**：开发者确认
这个设置的值是 **0.5x 或其它非 0 值**。`MotionDurationScale` 的那个特殊分支
（`if (durationScale == 0f) anim.durationNanos`）**只在恰好为 0 时触发**，
所以 §16 描述的现象在本设备上根本不会发生。

需要区分两件事：**机制真实存在**（库源码可证，设备上若真为 0 就一定会那样）与
**它是本次的原因**（不是）。把前者当成后者，就是这次多花一轮的原因。

§16 的改动**全部保留**，因为它们本身是净改进：自己数帧让时钟不再受系统设置影响、
错开初始相位让「不动」与「不存在」在现象上可区分、门控只冻结时间让最坏结果是静止而非消失、
切后台回来不再跳相位。但它们**并没有解决「看不到」**。

### 17.2 定位手段：不再推理，改为给设备装探针

前三次排查全部建立在推理上，被真机推翻两次。第四次改为**在应用里装探针**（诊断版，
`versionCode = 9`，事后已整体删除），把「看不到」拆成屏幕上能直接读的几个量：

- 洋红（#FF00FF）边框、左上角方块 → 证明**这一层真的在画**、画布的确切位置
- 每个光斑描一圈洋红细轮廓（圆心半径与光斑**同一套公式**）→ 证明位置公式与实际渲染一致
- 光斑透明度临时放大 3 倍（峰值 0.39）
- 黄底黑字读数：`vc`（装的是哪一版）、`anim`（系统动画程序时长缩放）、
  `frames`（本层自己数帧，与背景时钟同机制）、`state`（生命周期状态）

开发者的观察与结论：

| 观察 | 结论 |

| 看得到洋红方框 | 背景层确实在绘制，位置与尺寸正确 |
| 看得到洋红圆圈 | 光斑的圆心与半径与公式一致 |
| 洋红圆圈与灰云在缓慢上移 | **时钟在走** |

| 放大 3 倍后能看到「几大团浅灰色暗区」 | 浓度是唯一的问题 |

### 17.4 本次最该记住的一条

**像素差是「可见」的必要条件，不是充分条件。** 前三版都栽在把两者混为一谈：

- 本机复算只能回答「这个差在静态图像里是否可分辨」；
- 真机上玩家面对的是一大块**边缘极柔、移动极慢**的浅灰，而且**正在扫视棋盘找牌**，
  注意力根本不在背景上。
- 因此**「氛围型」视觉参数的验收判据只能是真机 A/B**，不能是本机计算值。
  诊断版就是那次 A/B —— 它的价值不在于「多做了什么功能」，而在于**把变量收敛到一个维度**。

（方法上的一个收获：本机虽无模拟器，但可以用**与 Kotlin 侧同一套公式**在 Python 里把背景
渲染成 PNG，作为「期望图像」与真机观察对照。本次用它验证了「位置公式与像素差算得对」；
但它的结论**不能**用来判定「人眼看不看得见」—— 那正是这一轮的教训。）

## 18. 修订 4：光斑改用主题色（真机反馈「灰色光斑太难看」）

修订 3 把浓度调到 0.36 之后，真机上终于看得见了 —— 但随即被否掉：**「灰色光斑太难看」**。
这条反馈的性质和前三轮都不同：前三轮是「功能没达成」，这一轮是「达成了但不好看」。

**又一次印证了 §17.4 的那句话**：可见性只能靠真机 A/B 定，而**好看与否更只能靠真机定** ——
本机既渲染不了，也没有「观感」这个量。单测能做的是两件事：把「不低于某条可见线」钉住，
以及**把已经否掉的做法写成断言防止回退**。

### 18.1 为什么灰会难看

底基本身是近白（`#F8F9FC`）且**没有色相**。在这样一块底上，中性灰的薄雾做不出「氛围」，
只会把画面弄脏 —— 它唯一的视觉效果就是「这里暗了一块」。要有氛围，薄雾必须带色相。

### 18.2 选色：只有 tone 40 的强调色同时满足「有色相」与「够得着可见线」

逐角色的实测相对亮度（`background` 约 242）：

| 候选 | 相对亮度 | 合成后的通道极差 | 结论 |
|---|---|---|---|
| `primary` / `tertiary` | 28.5~28.9 | **22~77** | **采用**：明暗差实测 **107~138 级**（落在真机已证实的可见区间内），且带明确色相 |
| `secondary` | 28.7 | ≈15 | 不用：明暗够，但它是**低彩度**（chroma 16）的强调色，合成后看上去仍是一片灰 —— 正是本次要摆脱的东西 |
| `error` | 28.7 | ≈60 | **禁止**：红色在连连看里是「错误」的语义色（FR-4.4 / FR-4.5 的红色抖动与描边） |
| `*Container` | 130~195 | 受明度限制 | 不用：它们与近白底色的差只有 30~113 级；要在近白底上叠出足够的明暗差就得叠到接近不透明，那时它已不像「氛围」而像色块 |

最终取 **`primary` + `tertiary`**（两个 tone 40 的强调色），于是 4 套主题色各自呈现自己的
两个色相：浅蓝+紫 / 黄绿+绿 / 玫红+橙 / 琥珀+橄榄。

### 18.3 与游戏状态色共用色相，为什么这次可以接受

修订 3 之前，本文件刻意**不用**任何强调色，理由是「`primary` 承载选中、`tertiary` 承载提示」。
改用主题色后必然共用色相，因此逐条复核：

- 背景是 **0.40 的半透明薄雾**，不是实色。选中/提示/错误的**描边**用的是 tone 40 实色
  （相对亮度约 28.8），与薄雾（约 122~150）的对比度仍有约 **4.6:1** —— 描边依旧清晰。
- **牌本身是不透明的**（`TileFaceBox` 的 `*Container` 底色），薄雾盖不到它，因此「选中牌」
  与「未选中牌」的差别不受影响。
- 受影响的只有「牌与薄雾之间」的明暗关系，而薄雾把背景压得比牌**更暗**，牌于是成了
  「浅色方块浮在彩色薄雾上」。实测：未选中的牌亮度 195，薄雾在最浓处约 122~150 → 对比约
  **1.4~1.5:1**，比没有背景时的 1.22:1 反而**更清楚**。
- 唯一还会发糊的是「薄雾亮度恰好等于牌」的那一圈：与未选中的牌同亮度处发生在
  **透明度约 0.15** 处、与选中/提示牌同亮度处发生在**约 0.28** 处。这两圈无法消除
  （径向渐变的必经之处），只能靠峰值透明度把主体推离它们。

结论记入单测 `背景用色必须取自主题色 - 不得退化成灰`：**允许 `primary`/`secondary`/`tertiary`，
禁止 `error` 系，且合成后的通道极差必须 ≥ 18 级**（灰色只有约 5 级）。

### 18.4 顺带修正的一处度量错误

修订 3 的可见性断言用的是「最大单通道差」，而真机锚点其实是按**明暗**感知的。
改用主题色后两者差异变大（色相变化大、明暗变化小的情况会被前者高估），因此把断言换成
**WCAG 相对亮度差**，并把两个真机锚点换算到同一刻度上重新标定：

| 锚点 | 明暗差 | 真机结果 |
|---|---|---|
| 修订 2 最强的一路 | 约 52 级 | 看不出 |
| 诊断版 | 约 137 级 | 看得很清楚 |
| 修订 3（灰） | 约 140 级 | 看得见，但颜色被否 |
| **修订 4** | **107~138 级**（通道极差 22~77） | 待确认 |

下界取 100（两锚点之间、偏向可见一侧）；渐变最暗端实测会让差值降到 93~103，已在余量内。
同时把透明度倍率从 `0.8/0.9/1.0/0.85` 收紧到 `0.9/0.95/1.0/0.92`：下界是按**最弱那一路**
卡的，档位差太大就会逼着峰值为最弱一路让路，导致最强的几路过浓、画面不均匀。
