## 1. 范围界定

SRS FR-11.4 的原文是「皮肤选择（**图案/配色**主题）」—— 严格说皮肤包含图案**与**配色。因此分两级：

| 级别 | 内容 | 本计划 |
|---|---|---|
| **Level 1** | 皮肤 = 图案集；可切换、可持久化、可在设置页预览 | ✅ **本次做** |
| Level 2 | 皮肤还携带一套 `ColorScheme`，驱动 `LianLianKanTheme` | ❌ 留给 V1.3，理由见 §5.4 |

**明确不做**：把 emoji 换成矢量素材。这属 FR-13.7 允许的另一条路线，成本高一个量级，且与本计划的「让皮肤可切换」无关（见 §6 R-1）。

## 3. 逐项设计

### J-1 拆出 `TileFaceBox`，牌面视觉与交互分离

**问题**：设置页做皮肤预览时需要渲染牌面，但 `TileView` 要求传入真实的 `Tile` 领域对象
（`fun TileView(tile: Tile, cellSize, onClick, modifier, enabled, isRejected, alpha, extraScale)`）。
若照现状使用，设置页就得伪造 `Tile(id, type, row, col)` —— 在 UI 层造领域对象是不合适的。

**做法**：拆成两层，视觉部分不依赖 `Tile`：

```kotlin
/** 纯视觉：只认一个图案字符与一组呈现参数。 */
@Composable
fun TileFaceBox(
    face: String,
    cellSize: Dp,
    modifier: Modifier = Modifier,
    enabled: Boolean = true,
    isRejected: Boolean = false,
    alpha: Float = 1f,
    extraScale: Float = 1f,
    onClick: () -> Unit = {},
)

/** 棋盘上的牌：解析出图案后交给 TileFaceBox。 */
@Composable
fun TileView(tile: Tile, ...) =
    TileFaceBox(face = LocalTileSkin.current.faceAt(tile.type), ...)
```

**收益**：设置页预览与棋盘渲染共用同一段视觉代码，杜绝「预览好看、实际不一样」。
预览时 `onClick` 用默认的空操作即可。

**调用方影响**：`BoardView` 的两处 `TileView(...)` 调用**无需改动**（`TileView` 签名不变）。

### J-2 引入 `TileSkin` 与 `LocalTileSkin`，把 skinId 接到渲染层

**新增 `ui/theme/Skin.kt`**：

```kotlin
/** 一套皮肤：图案集 + 展示名。Level 2 若加入配色，只在本类追加字段即可。 */
data class TileSkin(
    val id: Int,
    @StringRes val nameRes: Int,
    val faces: List<String>,
) {
    /** 取图案类型对应的显示字符；越界或负数一律按取模兜底，不抛异常。 */
    fun faceAt(type: Int): String = faces[type.mod(faces.size)]
}

/** 皮肤注册表。 */
object TileSkins {
    const val DEFAULT_ID = 0
    val all: List<TileSkin>
    val default: TileSkin get() = byId(DEFAULT_ID)
    /** 未注册的编号回退到默认皮肤。 */
    fun byId(id: Int): TileSkin = all.firstOrNull { it.id == id } ?: all[DEFAULT_ID]
}

/** 皮肤是跨屏幕的呈现配置，用 CompositionLocal 提供。 */
val LocalTileSkin = compositionLocalOf { TileSkins.default }
```

**改动点**：

| 文件 | 改动 |
|---|---|
| `ui/theme/Skin.kt` | 新增（含 `TileSkin` / `TileSkins` / `LocalTileSkin`） |
| `ui/theme/Theme.kt` | `LianLianKanTheme(darkTheme, skinId = TileSkins.DEFAULT_ID)`，内部 `CompositionLocalProvider` |
| `MainActivity` | 传 `skinId = settings.skinId` |
| `ui/game/TileFaces.kt` | **删除**，两套图案数据与解析逻辑并入 `TileSkins` |
| `ui/game/TileView.kt:136` | 改读 `LocalTileSkin.current.faceAt(tile.type)`（经 J-1 落在 `TileView` 一层） |
| `ui/game/TileFacesTest.kt` | 迁移为 `ui/theme/SkinTest.kt` 并随新 API 调整 |

**为什么放 `ui/theme` 而不是留在 `ui/game`**：设置页也要用（预览），属跨屏幕的呈现配置，
与已有的 `Color` / `Shape` / `Theme` 同类。

**为什么不加第三套皮肤**：见 §9 待确认项。

### J-3 设置页皮肤预览与切换

**现状**：主题是三个 `RadioButton` 文字单选。**皮肤不应照抄这个形式** —— 它是视觉选择，
用纯文字等于让用户盲选。

**做法**：预览卡片列表，每张卡片包含：
- 该皮肤的 **3 个示例牌面**（用 J-1 的 `TileFaceBox` 渲染，不伪造 `Tile`）；
- 皮肤名（`stringResource(skin.nameRes)`）；
- 选中态：卡片边框用 `colorScheme.primary`，与主题视觉一致。

点击即调用 `viewModel.onSkinIdChange(skin.id)`。

**新增字符串**：`settings_skin`（皮肤）、`skin_fruits`（水果）、`skin_animals`（动物）。

**立即生效**：`skinId` 从 `settingsRepository.settings` 流下来 → `MainActivity` →
`LianLianKanTheme` → `LocalTileSkin`，因此切换后重组即生效，无需重启（满足 FR-11.6）。

### J-4 测试

**保留全部既有不变量**（从 `TileFacesTest` 迁移）：
- 每套皮肤的图案数 ≥ 关卡所需的最大 `typeCount`；
- 同一皮肤内图案互不相同、且均非空；
- 未注册的皮肤编号回退到默认皮肤；
- 负数 / `Int.MIN_VALUE` 类型不抛异常。

**新增**：
- `TileSkins.all` 的 `id` 唯一，且注册顺序与下标一致（避免 `byId` 与下标混用出错）；
- 每个皮肤的 `nameRes` 不为 0；
- `LocalTileSkin` 的默认值是 `TileSkins.default`（否则 Preview 或未 provide 的场景会拿到错皮肤）；
- `TileSkin.faceAt` 对超出一套皮肤长度的类型能取模兜底。

**不动**：`ColorContrastTest`。Level 1 不改配色，无需参数化（这正是把 Level 2 分开做的收益之一）。

## 5. 关键设计决定

### 5.1 skinId 用 CompositionLocal 而非参数透传

| 方案 | 代价 |
|---|---|
| 参数透传（`GameScreen → BoardView → TileView` 各加一个 `skinId`） | 显式、好测；但**设置页预览也要皮肤数据**，会变成两处来源，容易出现「预览与实际不一致」 |
| CompositionLocal | 无参数穿透；依赖变隐式 |

**选 CompositionLocal**，理由：
1. 设置页预览与棋盘必须共用同一来源，否则迟早不一致；
2. `TileView` 是叶子组件，棋盘最多渲染 96 次，皮肤只被它需要 —— 这正是环境式呈现配置的典型场景；
3. 皮肤属于呈现层，放 `ui/theme` 与现有分层一致。

**对「隐式依赖」的缓解**：把**解析**与**管道**分开 —— 图案解析仍是纯函数（`TileSkin.faceAt`），
继续在 JVM 上单测；只有「从哪里拿皮肤」这一步是环境提供。这与 M8 处理 DataStore 映射的思路一致。

### 5.2 用 `compositionLocalOf` 而非 `staticCompositionLocalOf`

两者差别在于**变更时谁重组**：
- `staticCompositionLocalOf` 不跟踪读取者，值一变就重组**整个 content 子树**（Material 的
  `ColorScheme` 用它，因为主题切换罕见且要省掉每次读取的开销）；
- `compositionLocalOf` 跟踪读取者，只有真正读了它的组件才重组。

皮肤切换虽然也是用户动作、不频繁，但读它的只有约 96 个 `TileView`，
**没有必要让 HUD、操作条、连线画布这些无关组件跟着重组**，因此选 `compositionLocalOf`。

### 5.3 先做 J-1 拆分，再做 J-2 接线

顺序有意如此：先让「牌面视觉」与「`Tile` 领域对象」解耦，设置页的预览才有干净的复用点。
若先接线后拆分，`TileView` 会同时长出「读皮肤」与「接受裸图案」两个口子，反而更乱。

### 5.4 为什么把 Level 2（皮肤带配色）分开

`ColorContrastTest` 目前把断言写死在 `LightColors` / `DarkColors` 上（7 处引用）。
一旦皮肤携带配色，断言必须参数化为「对每套皮肤 × 深浅色都成立」——
这是一次独立的、需要重新设计检查矩阵的工作，**不适合塞进「让皮肤可切换」这一轮**。

本计划已为此留好口子：`TileSkin` 是数据类，将来加配色字段不影响任何调用方。

## 6. 风险

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| R-1 | **emoji 跨设备呈现差异大**（不同 Android 版本/厂商字体下可能彩色、单色、甚至显示为方框） | 中 —— 皮肤作为卖点时的观感 | 见下方说明 |
| R-2 | `LocalTileSkin` 默认值缺失 → Preview 或未 provide 的场景崩溃/串皮肤 | 中 | 默认值设为 `TileSkins.default`（非空），并加单测断言 |
| R-3 | 切换皮肤后棋盘不刷新 | 高 —— 功能看起来没生效 | 确保 `skinId` 确实接在 `settingsRepository.settings` 流上；V-2 专门验收 |
| R-4 | `TileFaces` 迁移时漏改引用 | 低 | 生产侧只有 1 处引用（`TileView:136`），编译期即可暴露 |
| R-5 | 新增皮肤时图案数不足（< 13）导致取模回绕、出现重复图案 | 中 | 既有不变量断言「每套皮肤图案数 ≥ 最大 typeCount」会在测试期拦住 |

**关于 R-1 的补充**：一个低成本的缓解办法是**再加一套基于文本符号的皮肤**（如
`▲ ● ■ ◆ ★ ♥ ♠ ♣ ♦ ✚ ✦ ❄ ✿`）。这类字符是普通 Unicode 字符、由系统字体渲染，
**跨设备一致性远好于 emoji**，既能作为第三套皮肤让切换效果更明显，
也能在 emoji 支持不佳的设备上充当兜底。是否加入见 §9。

## 10. 实施结果（2026-09-12）

四项设计全部落地，`versionCode` → 3、`versionName` → `"1.2"`，**186 个 JVM 单测全绿**。

| 项 | 状态 | 落地情况 |
|---|---|---|
| J-1 | 完成 | `TileView.kt` 拆为 `TileFaceBox`（承载全部牌面视觉）+ `TileView`（把 `Tile` 翻译成图案字符与状态标志的薄适配层）。`BoardView` 的两处调用无需改动 |
| J-2 | 完成 | 新增 `ui/theme/Skin.kt`；`LianLianKanTheme` 新增 `skinId` 参数并 `CompositionLocalProvider` 下发；`MainActivity` 传 `settings.skinId`；`TileFaces.kt` 与其测试已删除 |
| J-3 | 完成 | 设置页新增皮肤区块，三张预览卡片（各渲染 3 个真实牌面 + 名称 + 选中边框），点击即 `onSkinIdChange` |
| J-4 | 完成 | `TileFacesTest`(8) 迁为 `SkinTest`(11)，既有不变量全部保留，新增注册表一致性检查 |
| J-5 | 完成 | SRS 发布 V1.5；README 更新已知取舍与版本表 |

**三套皮肤**：蔬果（默认，13 个 emoji）、动物（13 个 emoji）、符号（13 个 Unicode 几何字符）。

**与计划的三处差异**：

1. **J-1 的拆分形态与计划草稿不同**。计划写的是「`TileFaceBox` 只画卡片、`TileView` 在外层套发光/描边」，实际实现时发现那样会让描边与发光分属两层、分层关系混乱。改为 **`TileFaceBox` 承载全部视觉**（外发光 + 卡片底 + 描边 + 图案 + 按压反馈），`TileView` 只做翻译。因此 `TileFaceBox` 的状态标志（`isSelected` / `isHinted`）是**入参**而非从 `Tile` 推导 —— 预览场景没有 `Tile`，这正是拆分的意义。
2. **`LocalTileSkin` 的默认值无法单测**。计划 J-4 写的是「断言 `LocalTileSkin` 的默认值是 `TileSkins.default`」，但 `CompositionLocal.defaultValue` 是 Compose 内部 API，单测取不到。改为断言 `TileSkins.default` 本身自洽（默认值就取自它），并在 `SkinTest` 的类注释里写明这一覆盖盲区。
3. **符号皮肤避开了 ♥ ♠ ♣ ♦ ❄**。这些字符带 emoji 变体，在部分设备上会被渲染成彩色 emoji —— 恰是本皮肤想避免的情况。改用 `▲ ▼ ■ ● ◆ ★ ✚ ✦ ✿ ◐ ▣ ◈ ⬢`。

**仍需真机确认**：§4 的 V-1 ~ V-6，其中 **V-4（各套皮肤在本机都能正常显示、不出现方框）** 是本轮最需要实测的一条 ——
emoji 与几何字符的实际呈现依赖设备字体，编码侧无法验证。
另外 **`@Preview` 是验证 R-2（CompositionLocal 默认值）的唯一途径**，建议在 Android Studio 里看一眼 `TileFaceBox` 的预览。
