## 2. 逐项说明

### I-1 错误反馈后不保留第一张牌的选中态

**现状**：`GameSession.select` 在「图案相同但不可连通」时保留第一张牌的 `SELECTED` 状态，
以便玩家直接改选搭档；这是 V1.0 确认过的决策 **D-4**，并已写入 SRS V1.2 的 UC-03 步骤 3.b.ii 与 FR-4.4。

代码位置：`domain/session/GameSession.kt` 的 `NoPath` 分支（当前为 `snapshot.copy(board = board, ...)`，
其中 `board` 保留了第一张的选中态）。

**目标行为**：出错后第一张不再保持选中。

**需要明确的歧义**：AC-07 覆盖两类错误，而它们当前行为不同：

| 场景 | 当前行为 | 说明 |
|---|---|---|
| ① 图案不同（`WrongType`） | 选中**转移给第二张**（第一张已不选中） | SRS FR-4.5 明确规定「将第二张牌设为选中」 |
| ② 同图案但连不通（`NoPath`） | 第一张**保持选中** | 本次要改的就是这里 |

按「出错后第一张不保持选」的字面要求，只有 ② 需要改：**把选中态清空**（第一张、第二张都不再选中）。
① 已经满足「第一张不保持选」，且 SRS FR-4.5 对它有明确要求，**建议不动**。

**待确认**：② 改完后是「完全清空选中」还是「改为选中第二张（与 ① 一致）」？
本计划按前者（完全清空）推进 —— 它更贴合「出错就回到未选状态」的直觉，
也让玩家的下一次点击总是从干净状态开始。若希望与 ① 一致，请在动手前指出。

**验收标准**：
- 点两张图案相同但连不通的牌 → 红闪抖动 + 文案提示，**两张牌均不再高亮**；
- 紧接着点任意一张牌 → 能正常作为「第一张」被选中（无需先取消）。

**对 SRS 的影响**：需发布 SRS V1.3，修订 UC-03 步骤 3.b.ii 与 FR-4.4，
把 V1.2 写入的「保留第一张牌的选中态」改回「清空选中态」，并在修订历史中记录 D-4 被撤销的原因。

**对单测的影响**：两个用例需重写（它们当前断言的正是要改掉的行为）：
- `GameSessionTest.图案相同但不可连通时不消除并保留第一张的选中态`
- `GameSessionTest.连通失败后可直接改选其他搭档`

### I-2 提示文案「后到即替换」，不再排队

**现状**：`ui/game/GameScreen.kt` 用 `scope.launch { snackbarHostState.showSnackbar(...) }` 弹提示。
`showSnackbar` 会**挂起到该提示消失**（Material 3 默认约 4 秒），因此连续触发多次错误时，
提示会**一条条排队**播放：第二次错误要等第一条显示完才出现。连点几次后，屏幕上的提示与实际操作严重脱节。

**目标行为**：新提示立即顶掉旧提示，并且**从新提示出现的时刻重新计时**。

**实现方案**：改为自绘提示层（与 I-3 合并实施），核心是「一个状态 + 一个自增 token」：

```kotlin
var notice by remember { mutableStateOf<Notice?>(null) }   // Notice(text, token)
// 新提示到达：token = ++counter，notice = Notice(text, token) —— 旧提示被直接覆盖
LaunchedEffect(notice?.token) {                            // token 变化即重新计时
    if (notice != null) { delay(NOTICE_MILLIS); notice = null }
}
```

要点：
1. **不再使用 `SnackbarHostState`** —— 它的排队是设计行为，绕开它比对抗它更省事；
   而且 I-3 要求的样式（居中 + 浅色半透明）用 Material 3 的 Snackbar 也改不出来。
2. **token 作为 `LaunchedEffect` 的 key** 是关键：若只用文案做 key，连续两次相同文案
   （比如连点两次同样的错误）不会重启计时，第二条会提前消失。
3. 提示时长建议 **1800 ms**：比 Material 默认的 4 秒短，因为它是操作反馈而非需要阅读的通知。

**验收标准**：
- 连续快速触发 5 次不同错误 → 每次文案**立即**切换，界面上任何时刻只有一条提示，不出现排队；
- 连续触发 2 次**相同**错误 → 第二次仍从头计时（不会因为文案相同而提前消失）。

### I-3 提示文案居中 + 浅色半透明背景

**现状**：Material 3 `Snackbar` 的文字默认左对齐，背景取 `inverseSurface`（浅色主题下是深色底）。

**目标行为**：文字居中；背景为浅色半透明。

**实现方案**：随 I-2 的自绘提示层一起做：
- 文字 `textAlign = TextAlign.Center`；
- 容器用 `RoundedCornerShape` + 浅色半透明底。

**关于「浅色」在深色主题下的处理**：如果直接用白色半透明底 + 深色文字，
在深色主题下反而更醒目、且与牌面区分明显 —— 这恰好符合「浅色半透明」的字面要求，
两种主题下表现一致。因此**建议固定使用浅色底 + 深色文字**，而不是跟随主题切换明暗。

```kotlin
// 浅色半透明底：在深浅两种主题下都是"浅色半透明"，表现一致
background = Color.White.copy(alpha = 0.86f)
contentColor = Color(0xFF1B1B1B)
```

若更希望深色主题下用深色底，改成 `MaterialTheme.colorScheme.surface.copy(alpha = 0.9f)` 即可，
但那样深色主题下就不是「浅色半透明」了 —— **这一点按上述建议实施，如与预期不符请告知**。

**验收标准**：浅色与深色主题下，文案均水平居中、背景为浅色半透明、文字清晰可读，
且不遮挡棋盘关键区域（提示层位于底部操作条之上）。

### I-4 状态栏与 APP 统一 + 图标自动黑白

**现状与问题**（这一项核实后**不只是美化**）：

1. `MainActivity` **没有调用 `enableEdgeToEdge()`**，也没有任何 `WindowInsets` 处理
   （已核实：全项目除 `LevelSelectScreen` / `SettingsScreen` 的 `Scaffold` 外，无插边相关代码）。
2. 而 `targetSdk = 37`。**从 Android 15（API 35）起，targetSdk ≥ 35 的应用强制边到边**，
   且 `android:statusBarColor` 被弃用、设置无效。

   两者叠加的后果：在 Android 15+ 设备上，应用内容会绘制到状态栏下方，
   而 `GameScreen` 的 `GameHud`（顶部倒计时/得分/连击）与 `MenuScreen` 的标题
   **都没有避让状态栏**，会被状态栏区域遮挡或压住。
3. 窗口主题用的是平台主题（`android:Theme.Material.Light.NoActionBar` /
   `android:Theme.Material.NoActionBar`），它跟随**系统**日夜模式，
   而 APP 内的主题由用户设置决定 —— 当用户手动选择与系统相反的深浅色时，
   窗口层与 APP 层的表现可能不一致。

**目标行为**：
1. 状态栏区域颜色与 APP 背景一致；
2. 状态栏图标（时间、信号、电量）根据其下方背景的明暗**自动切换黑/白**；
3. 顶部内容不被状态栏遮挡（这是上面第 2 点的直接后果，必须一并解决）。

**实现方案**：
1. `MainActivity.onCreate` 中调用 `enableEdgeToEdge()`（`androidx.activity`，已在依赖中）。
2. 用 `WindowInsetsControllerCompat(window, window.decorView).isAppearanceLightStatusBars = !darkTheme`
   控制图标黑白，在 `darkTheme` 变化时通过 `SideEffect` 同步。
   由于边到边后状态栏透明、露出 APP 自己的渐变背景，**「颜色统一」是自动达成的**，
   不需要再设 `statusBarColor`（在 API 35+ 上设了也无效）。
3. **为各屏幕补插边避让**，这是本项最容易漏的部分。逐屏处理：

   | 屏幕 | 处理方式 |
   |---|---|
   | `GameScreen` | HUD 顶部加 `Modifier.windowInsetsPadding(WindowInsets.statusBars)`；底部操作条加 `WindowInsets.navigationBars` |
   | `MenuScreen` | 内容整体加状态栏插边 |
   | `LevelSelectScreen` / `SettingsScreen` | 已用 `Scaffold`，改为显式传入 `contentWindowInsets`，避免与顶栏重复计算 |
   | 暂停 / 结算弹窗 | `AlertDialog` 自行处理，无需改动 |

4. 窗口主题（`values/themes.xml`）保持平台主题不动 —— 边到边后它的状态栏颜色已不起作用，
   而它的 `windowBackground` 仍是启动瞬间的底色。若要彻底一致，可让 `windowBackground`
   用与 APP 浅/深底色相近的静态色，减少冷启动时的闪白。**建议一并处理**（成本极低）。

**验收标准**：
- 浅色 / 深色 / 跟随系统三种设置下，状态栏区域颜色与 APP 背景连续、无突兀色块；
- 状态栏图标在浅色背景下为深色、深色背景下为浅色，**切换主题后立即变化**；
- 顶部 HUD（倒计时/得分/连击）与主菜单标题**完整可见，不被状态栏压住**；
- 在 Android 15+ 与 Android 14 及以下设备上均正常（这是本项最需要真机确认的部分）。

**风险**：中。边到边是全局性改动，容易在某个屏幕上漏加插边或插边重复（表现为顶部/底部多出一块空白）。
计划在改完后逐屏人工核对，并把「Android 15+ 与旧版本各验证一次」写进真机验收清单。

### I-5 游戏界面显示当前关卡

**现状**：`GameHud` 只有「时间 / 得分 / 连击」三块（已核实），不显示关卡号。

**目标行为**：游戏界面显示当前是第几关。

**实现方案**：
- 数据已经就绪：`GameState.config.level` 即关卡编号，无需新增状态；
- 在 `GameHud` 左侧增加一块「第 N 关」，右侧保持三块；
- 文案用现有资源 `R.string.level_number`（`"第 %1$d 关"`，关卡选择页已在用），保持措辞一致；
- **注意窄屏**：一行四块在 360dp 上偏挤（「第 10 关」约需 56dp + 三块标签宽度）。
  若实测拥挤，备选方案是把关卡做成一行的标题放 HUD 上方，或把「连击」在无连击时收起。
  **先按一行四块实现，真机看效果再调。**

**验收标准**：进入任意关卡（含从关卡选择页进入、通关后「下一关」、失败后「重试」），
HUD 显示的关卡号均与实际关卡一致；「下一关」后数字递增。

**对 SRS 的影响**：SRS 5.1 的界面清单里，游戏主界面只写了「顶部：倒计时、当前得分、连击」，
未提关卡号。需在 SRS V1.3 的 5.1 与 FR-1.4 附近**补充关卡展示要求**（属需求补充，非缺陷修复）。

## 7. 实施结果（2026-09-12）

5 项改进全部实现，`versionCode` → 2、`versionName` → `"1.1"`，182 个 JVM 单测全绿。

| 编号 | 状态 | 落地位置 |
|---|---|---|
| I-1 | 已完成 | `GameSession.select` 的 `NoPath` 分支改为 `clearSelection(board)`；单测改为断言「两张牌都回到 NORMAL 且无残留高亮」 |
| I-2 | 已完成 | `GameScreen` 移除 `SnackbarHostState`，改为 `notice` + 自增 `noticeToken`；`LaunchedEffect(notice?.token)` 负责 1800ms 后消失 |
| I-3 | 已完成 | 新增 `NoticeBanner`：`TextAlign.Center` + 固定浅色半透明底（`Color.White.copy(alpha = 0.86f)`）+ 深色文字 |
| I-4 | 已完成 | `MainActivity` 调用 `enableEdgeToEdge()` 并用 `WindowCompat.getInsetsController(...).isAppearanceLightStatusBars = !darkTheme` 同步图标黑白；`GameScreen` 的 HUD / 操作条分别避让 `statusBars` / `navigationBars`，`MenuScreen` 避让 `systemBars` |
| I-5 | 已完成 | `GameHud` 增加「关卡」块，取 `state.config.level`；新增资源 `hud_level` |

**SRS 已同步至 V1.3**：撤销 V1.2 关于「保留第一张选中」的规定（UC-03 步骤 3.b.ii 与 FR-4.4 改为清空选中态），
5.1 游戏主界面顶部增补「当前关卡」，修订历史记录本次撤销的原因。

**两处实施细节与计划的差异**：

1. **提示条未加淡入淡出动画**。计划里没写，但实现时特意**没加** —— I-2 的要求是「前一条立刻消失、立即显示最新的」，
   任何过渡动画都会削弱「立刻」这一感受。这一条已写进 `NoticeBanner` 的注释。
2. **`Scaffold` 的两个屏幕未改动**。计划里提到要显式传 `contentWindowInsets`，实际核查后
   `LevelSelectScreen` / `SettingsScreen` 用的是 Material 3 `Scaffold` + `TopAppBar`，
   二者已各自处理系统栏插边，再显式传入反而有重复计算导致空白的风险，因此**保持默认**。

**仍需真机确认（编码侧无法覆盖）**：第 5 节的 V-1 ~ V-7，
其中 **V-5（Android 15+ 与 Android 14 及以下各验证一次顶部内容不被遮挡）** 是本轮最需要实测的一条 ——
边到边是全局性改动，且当前环境无法启动模拟器。
