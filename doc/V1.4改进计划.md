## 1. 现状核查

### 1.1 图标（需求 ①）

| 项 | 现状 |
|---|---|
| 自适应图标（API 26+） | `mipmap-anydpi-v26/ic_launcher.xml` 与 `ic_launcher_round.xml`，引用 `drawable/ic_launcher_foreground.xml`(1.7KB) 与 `ic_launcher_background.xml`(5.6KB) |
| 光栅图标（API 24–25） | `mipmap-{m,h,xh,xxh,xxxh}dpi/ic_launcher.webp` 与 `ic_launcher_round.webp`，共 10 个文件 |
| 内容 | **全部是 Android Studio 模板素材**（绿色机器人那套），与本游戏无关 |
| monochrome 层 | 自适应 XML 里已声明，但指向同一个模板前景 drawable |

> ⚠️ **关键约束**：`minSdk = 24`，因此 **API 24–25 的设备读取的是 `mipmap-*dpi/*.webp` 光栅**，
> 而**不是**自适应矢量。只替换矢量的话，老设备上仍是原来的机器人图标。
> 换图标必须**同时**产出矢量与光栅两轨。

### 1.2 启动白屏（需求 ②）

| 项 | 现状 |
|---|---|
| 窗口主题 | `values/themes.xml` 仅 `<style name="Theme.LianLianKan" parent="android:Theme.Material.Light.NoActionBar" />`，**未设置 `windowBackground`**，也无任何启动画面配置 |
| 启动画面库 | **未引入** `androidx.core:core-splashscreen` |
| `activity-compose` | 1.13.0（已足够支持 `installSplashScreen()` 所需的生命周期） |
| 深色主题 | `values-night/themes.xml` 已在 V1.3 删除（深色模式整体移除） |

**白屏根因**：冷启动时系统先绘制窗口主题的 `windowBackground`（平台默认是白色），
Compose 的首帧要等 `onCreate` → `setContent` → 首次组合完成才出现。
这段空档显示的就是那块白底，没有品牌信息、也没有过渡。

**还有第二处闪烁（容易被忽略）**：`MainActivity` 目前这样写：

```kotlin
val settings by settingsRepository.settings.collectAsStateWithLifecycle(initialValue = Settings())
```

`Settings()` 的默认 `themePaletteId = 0`。**若玩家选的是其他主题色，冷启动会先按默认浅蓝渲染，
读到 DataStore 的真实值后再跳到所选配色** —— 这是一次可见的颜色跳变，与白屏叠加在一起。

因此「启动白屏」实际由两个独立成因构成，计划中分别处理。

## 2. 需求 ①：APP 图标

### 2.1 设计构想（待确认，见 §9 Q1）

核心玩法是「两块图案相同的牌，用**不超过 2 个拐点**的折线连通」。图标直接编码这件事：

```
┌─────┐         ┌─────┐
│  ●  │         │  ●  │       两块同图案的圆角牌，
└──┬──┘         └──┬──┘       由一条两折连线相接
   └──────┬───────┘
          └──────────  ← 折线（2 个拐点）
```

三种备选（§9 Q1 里选）：
- **A（推荐）**：两块同图案圆角牌 + 一条两折连线。**直接表达玩法**，缩到 48dp 仍可辨识
- **B**：单块牌内嵌一条折线。更简洁，但「连连看」的语义弱一些
- **C**：四个圆点排成方形、两条线连接成「连」的意象。抽象、好看，但看不出是游戏

### 2.2 单一来源生成器（推荐做法）

设计要在**两处**落地（矢量 + 光栅），若各写一份必然漂移。因此新增
`tools/generate_icon.py`（纯标准库，与 `tools/generate_sfx.py` 同一套路数），
**从同一份形状定义同时产出**：

| 产物 | 用途 | 说明 |
|---|---|---|
| `drawable/ic_launcher_background.xml` | 自适应图标背景层 | VectorDrawable，纯色/渐变 |
| `drawable/ic_launcher_foreground.xml` | 自适应图标前景层 | VectorDrawable，108dp 画布、安全区 66dp |
| `drawable/ic_launcher_monochrome.xml` | Android 13+ 主题图标 | 单色剪影（当前 monochrome 层复用了前景，应独立） |
| `mipmap-{m,h,xh,xxh,xxxh}dpi/ic_launcher.png` | API 24–25 方形图标 | 48/72/96/144/192 px |
| `mipmap-{m,h,xh,xxh,xxxh}dpi/ic_launcher_round.png` | API 24–25 圆形图标 | 同上，圆形遮罩 |

**为什么用纯标准库写 PNG**：PNG 就是 zlib 压缩的扫描行 + 若干 chunk，用 `zlib`+`struct`
即可写出，不需要 Pillow。栅格化用**超采样**（例如 4× 渲染再降采样）做抗锯齿，
避免边缘锯齿。这与项目此前用脚本自制音效素材（`generate_sfx.py`）的做法一致，
产物可重复生成、可 diff 审查。

**旧文件清理**：10 个模板 `.webp` 删除，改为同名 `.png`。

### 2.3 图标配色（待确认，见 §9 Q2）

**硬约束：启动图标无法跟随 APP 内的主题色设置。** 自适应图标是静态资源，
运行期改不了（除非用 `activity-alias` 切换，代价大且会在桌面上留下多个入口）。
因此图标只能用**一套固定品牌色**。

建议：用默认主题色（浅蓝 `#8FD3F6`）的 `primary`（tone 40）作为牌面主色，
配 M3 的 `onPrimary`/容器色作对比 —— 与 APP 默认观感一致。

## 3. 需求 ②：启动白屏

### 3.1 方案总览

引入 **`androidx.core:core-splashscreen`**（官方向后兼容库，API 24 起可用）：

1. **新增启动主题** `Theme.LianLianKan.Starting`（parent = `Theme.SplashScreen`），配置：
   - `windowSplashScreenBackground`：启动底色
   - `windowSplashScreenAnimatedIcon`：新图标（需求 ① 的产物）
   - `postSplashScreenTheme`：`@style/Theme.LianLianKan`（退出启动画面后切回应用主题）
   - `windowLightStatusBar = true`：与 V1.3 的边到边 + 深色状态栏图标一致
2. **清单**把 `android:theme` 指向启动主题
3. **`MainActivity`** 在 `super.onCreate` 之前调用 `installSplashScreen()`
4. **按住启动画面，直到设置读完**（解决 §1.2 的第二处闪烁）：

```kotlin
val splash = installSplashScreen()
splash.setKeepOnScreenCondition { !settingsLoaded }
```

需要一个「设置已读到首个真实值」的信号。`SettingsRepository.settings` 是 `Flow`，
建议在仓库层补一个 `val isLoaded: StateFlow<Boolean>`（或用一个 `Flow<Settings>` 的
`onEach { loaded = true }` 包装），**不要**用 `delay` 之类的定时猜测。
再加一个兜底超时（例如 1.5s），避免 DataStore 异常时启动画面卡死 —— 这是必须的，
否则「读不到设置」会变成「应用起不来」。

### 3.2 启动底色怎么选（一处需要判断的地方）

启动画面的底色在**主题里写死**，而 APP 的底色由 4 套配色之一生成的 `background` 决定 ——
启动时还不知道玩家选了什么。

好在：M3 的**中性色受种子色影响很小**（4 套配色的 `background` 都是带极轻色相的近白色），
因此取一个固定近中性色即可，出屏时的色差肉眼几乎不可见。

**推荐**：取某个中性 `background`（如浅蓝主题的 `background`）作为固定值，
并在代码注释里写明「4 套配色的 background 差异极小，故固定值不会造成可见跳变」。
若实测发现有色差，备选方案是把启动底色改成**与图标一致的品牌色**（明显的品牌色块出屏），
反而比「接近但不完全一致」更自然。

## 4. 风险

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| R-1 | 矢量与光栅两轨漂移（改了矢量忘了重生成光栅） | 中 —— 老设备显示旧图标 | 单一来源生成器（§2.2）；并在 README 写明「改动图标必须重跑 `generate_icon.py`」 |
| R-2 | 纯 Python 栅格化的抗锯齿质量不如专业工具 | 低 —— 小尺寸下可能略有毛边 | 超采样 4×；真机确认 48dp 下的观感 |
| R-3 | `setKeepOnScreenCondition` 依赖 DataStore 首值，异常时可能卡死启动画面 | **高 —— 应用起不来** | 必须加超时兜底（§3.1 第 4 点）；超时后强制放行 |
| R-4 | 启动底色与所选主题的 `background` 存在细微色差 | 低 | 固定近中性色（§3.2）；真机在 4 套主题下各看一次 |
| R-5 | 自适应图标安全区裁切（前景超出 66dp 安全区会被切掉） | 中 —— 图标被削边 | 前景设计限制在中心 66dp 圆内；真机用「设置 → 壁纸」或长按图标查看多种遮罩形状 |
| R-6 | 图标无法跟随主题色，与 APP 内观感不一致 | 低（且不可解） | 用默认主题色作为固定品牌色（§2.3）；在 README 记为已知约束 |

## 9. 待确认项

### Q1：图标用哪个概念？

- **A（推荐）**：两块同图案圆角牌 + 一条两折连线 —— 直接表达「≤2 拐点连通」的核心玩法
- **B**：单块牌 + 一条折线 —— 更简洁，语义稍弱
- **C**：四点两线的抽象构成 —— 好看但看不出游戏类型

### Q2：图标配色

**先说明一个硬约束**：启动图标**无法跟随 APP 内的主题色设置**（自适应图标是静态资源，
运行期改不了）。因此图标只能用一套固定品牌色。

- **A（推荐）**：用默认主题色（浅蓝）的 `primary`（tone 40）+ 中性底色，与 APP 默认观感一致
- **B**：用一个与 4 套主题色都不同的独立品牌色（如深靛蓝），让图标更像「独立品牌」
- **C**：中性灰白 + 单色折线，最克制，但在应用列表里不够显眼

**另外**：V1.3 的已知问题「`primary` 偏暗」（见 V1.3 计划 §12）会直接影响图标观感 ——
若 Q2 选 A，图标会用上那个偏暗的 tone 40。若希望图标更明快，
可以**单独为图标取一个更浅的色**（图标不受 APP 配色约束，本来就可以独立取色）。

---

**以上 2 项确认后即可动手。** 其中 Q1 决定设计方向，Q2 只影响取色、可以后调。
