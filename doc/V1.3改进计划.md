## 1. 两项需求的解读

给定的 5 个主题色：

| 编号 | 色值 | 观感 |
|---|---|---|
| `BLUE` | `#8FD3F6` | 浅蓝 |
| `LIME` | `#ABCA14` | 黄绿 |
| `PINK` | `#FE2472` | 玫红 |
| `AMBER` | `#FFBA07` | 琥珀 |
| `CRIMSON` | `#D71418` | 正红 |

**需求 ①「把深浅色与跟随系统改为 5 种主题色」** 很清楚：主题选择器由
`{跟随系统, 浅色, 深色}` 换成 `{浅蓝, 黄绿, 玫红, 琥珀, 正红}`。

**需求 ②「FR-11.4 的 Level 2」** 指皮肤携带配色。FR-11.4 的原文是「皮肤选择（**图案/配色**主题）」——
斜杠并列，本就可读作**两个维度**。因此两项需求合起来有一个关系问题需要定：

| 方案 | 含义 | 后果 |
|---|---|---|
| **A（推荐）** | 配色与图案**正交**：5 种主题色是一个选择器，3 套皮肤是另一个选择器 | 组合 5 × 3 = 15 种观感；两个维度互不干扰；FR-11.4 的「图案/配色」正好对应这两个选择器 |
| **B** | 皮肤**绑定**配色：切皮肤即切配色，取消独立的主题色选择器 | 3 套皮肤对不上 5 种配色，需要重新定义皮肤集合（例如扩到 5 套皮肤，每套一个图案集 + 一种配色）—— 意味着要新设计 2 套图案 |

**推荐 A**。理由：A 让两项需求同时成立且互不打架；B 会强迫「皮肤数量 = 配色数量」，
而这两件事本来没有必然联系（玩家可能喜欢动物图案但不喜欢玫红）。

> 若选 A，`TileSkin` 仍可携带一个 `preferredPaletteId` 作为「皮肤携带配色」的字面落地 ——
> 首次切到某皮肤时自动套用它的推荐配色，玩家之后仍可单独改。**这属可选增强，见 §9 的 Q1b。**

## 3. 配色方案设计

### K-1 数据模型

```kotlin
// ui/theme/Palette.kt
data class ThemePalette(
    val id: Int,
    @StringRes val nameRes: Int,
    /** 开发者指定的色值；浅色模式下原样用作 primary（见 Q3）。 */
    val seed: Color,
    val light: ColorScheme,
    val dark: ColorScheme,
)

object ThemePalettes {
    const val DEFAULT_ID = 0            // 浅蓝
    val all: List<ThemePalette>
    val default: ThemePalette
    fun byId(id: Int): ThemePalette     // 未注册编号回退默认，与 TileSkins 同构
}
```

`Settings.themeMode: ThemeMode` 换成 `Settings.themePaletteId: Int`（或新枚举，见 Q2）。

### K-2 每套配色如何生成

**核心做法：不只换 primary，而是从 seed 派生出一整套 M3 颜色角色**，且**深色模式另有一套**。
中性色（`background` / `surface` / `onSurface` / `surfaceVariant` / `outline` 等）**沿用现有的中性灰阶**，
不随主题色变化 —— 这是刻意的：若每套主题色都重新定义中性阶，5 套观感的「质感」会变得不受控，
而主题色带来的差异本来就该集中在强调色上。

派生规则（每个角色给出目标，由 K-2 的求解器算出实际色值）：

| 角色 | 浅色主题 | 深色主题 |
|---|---|---|
| `primary` | **= seed 原值** | seed 提亮到在深底上可读 |
| `onPrimary` | 黑或白（按对比度自动选） | 同左 |
| `primaryContainer` | seed 极浅化 | seed 加深 |
| `onPrimaryContainer` | seed 深化 | seed 极浅化 |
| `secondary` | seed 降饱和 | seed 降饱和 + 提亮 |
| `tertiary` | seed **色相 +40°** | 同左 + 提亮 |
| `error` | 沿用现有标准红 | 沿用现有标准红 |

`tertiary` 取色相偏移是为了给「提示高亮」与「连线渐变」一个与主色可区分的强调色
（当前 `PathOverlay` 的渐变正是 primary → tertiary）。

### K-3 用「按对比度求解」而不是「按明度目标硬编码」

派生色的明度不能拍脑袋给定值 —— HSL 的 L 与 WCAG 对比度不是线性关系，
写死 `L = 0.78` 很可能在某个色相上恰好不达标。因此生成器采用**求解**：

```kotlin
/** 在保持色相/饱和度的前提下，二分搜索出满足目标对比度的明度。 */
fun tintMeetingContrast(
    seed: Color,
    background: Color,
    targetRatio: Double,   // 例如 4.5（正文）或 3.0（图形元素）
    preferDarker: Boolean,
): Color
```

**这样对比度是「由构造成立」的，而不是靠事后碰运气。** 事后仍有 `ColorContrastTest`
逐对复核（见 K-5），形成双保险。

**不引入新依赖**：不采用 `material-color-utilities`。理由有二 —— 一是它是基于 HCT 的完整
色调板方案，会产出与 `seed` 不同的 primary（取 tone 40/80），而开发者给的是**确切的色值**，
我们想让它原样出现；二是本项目一直保持依赖精简，而上述求解器只需几十行、且完全可单测。

### K-4 与皮肤的关系（Level 2 的落地）

- **方案 A 下**：`LianLianKanTheme(darkTheme, paletteId, skinId)` 两个维度各自 `CompositionLocalProvider`
  （`LocalTileSkin` 已有，新增 `LocalThemePalette` 或直接由 `MaterialTheme` 的 `colorScheme` 承载 ——
  后者更省事，配色本就走 `MaterialTheme.colorScheme`）。
- **可选的「皮肤携带配色」**：`TileSkin.preferredPaletteId`，见 §9 的 Q1b。

### K-5 对比度测试参数化（本项最大的测试工作量）

`ColorContrastTest` 目前把断言写死在 `LightColors` / `DarkColors` 上。V1.3 需要改为：

```kotlin
for (palette in ThemePalettes.all) {
    assertPairs("${palette.id} 浅色", palette.light, textPairs, MIN_CONTRAST)
    assertPairs("${palette.id} 深色", palette.dark, textPairs, MIN_CONTRAST)
}
```

即 **5 套 × 2 种深浅 = 10 套配色**全部过一遍 WCAG 断言（正文 4.5:1、图形元素 3:1）。
这让「新主题不会踩对比度坑」成为可回归的保证，而不是靠肉眼。

**新增断言（应对 Q3 的撞色问题）**：

- `primary` 与 `error` 在**同一套配色内**必须可区分 —— 对比度不低于 1.5:1，或明度差 ≥ 某阈值。
  红色主题（`#D71418`）下这是最容易出问题的一项：错误反馈的红闪若与选中高亮的红几乎一致，
  玩家就看不出「我点错了」。
- `primary` 与 `tertiary` 必须可区分（提示高亮与选中高亮同时出现时不能混淆）。

### K-6 设置页改动

主题区块由三个文字单选改为**色块选择**：一行 5 个圆形色块，每个填充该主题的 `primary`，
选中态加描边 + 对勾。与皮肤区块形成一致的语言（都是「看得见的选择」）。

需新增字符串：`settings_theme_color`（主题色）与 5 个色名（浅蓝 / 黄绿 / 玫红 / 琥珀 / 正红）。

## 9. 待确认项

### Q1：配色与图案的关系

- **A（推荐）**：两个独立选择器 —— 主题色（5 选 1）+ 皮肤（3 选 1），组合 15 种观感
- **B**：皮肤绑定配色，取消独立的主题色选择器；需要把皮肤扩到 5 套（要新设计 2 套图案集）

**Q1b（若选 A）**：是否让 `TileSkin` 携带 `preferredPaletteId`，即切皮肤时自动套用其推荐配色
（玩家之后仍可单独改）？这是「皮肤携带配色」的字面落地，但会引入一点耦合。

### Q2：深浅色的去留

需求 ① 的「**改为**」意味着替换掉三态。但这样会带来两个后果，需要你确认是否接受：

- **玩家将无法手动强制深浅色**，深色模式仅跟随系统；
- SRS FR-13.2「支持浅色 / 深色主题切换」需相应改写（NFR-5.3 的深色对比度要求仍会保留）。

| 选项 | 含义 |
|---|---|
| **Q2-a（推荐）** | 替换掉三态：只有 5 种主题色，深浅跟随系统。最贴合「改为」的字面，界面上少一个设置项 |
| **Q2-b** | 保留两个维度：主题色（5 选 1）+ 深浅（跟随系统 / 浅色 / 深色），即 5 × 3 = 15 种组合 |
| **Q2-c** | 替换掉三态，且**完全取消深色模式**，5 套主题色各自只有一套浅色方案 |

**Q2-c 不建议**：会与 NFR-5.3（深色对比度）直接冲突，且夜间观感会明显退化。

### Q3：给定的 5 个 hex 是否原样出现

- **Q3-a（推荐）**：作为**浅色模式下的 `primary` 原值使用**，让开发者给的色值原样可见；
  深色模式下提亮到可读亮度
- **Q3-b**：作为种子色交给标准 M3 色调板算法，产出的 primary 会是该色的某个色调
  （约等于「同色系但更柔和」），**原 hex 不会字面出现**

推荐 a —— 给了确切色值通常就是想在界面上看到它。若你其实想要「以这些色为基调的柔和主题」，
请选 b。
