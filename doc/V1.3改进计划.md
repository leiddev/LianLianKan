## 1. 两项需求的解读

给定的 5 个主题色：

| 编号 | 色值 | 观感 |
|---|---|---|
| `BLUE` | `#8FD3F6` | 浅蓝 |
| `LIME` | `#ABCA14` | 黄绿 |
| `PINK` | `#FE2472` | 玫红 |
| `AMBER` | `#FFBA07` | 琥珀 |
| `CRIMSON` | `#D71418` | 正红 |

**需求 ①「把深浅色与跟随系统改为 5 种主题色」** 很清楚：主题选择器由
`{跟随系统, 浅色, 深色}` 换成 `{浅蓝, 黄绿, 玫红, 琥珀, 正红}`。

**需求 ②「FR-11.4 的 Level 2」** 指皮肤携带配色。FR-11.4 的原文是「皮肤选择（**图案/配色**主题）」——
斜杠并列，本就可读作**两个维度**。因此两项需求合起来有一个关系问题需要定：

| 方案 | 含义 | 后果 |
|---|---|---|
| **A（推荐）** | 配色与图案**正交**：5 种主题色是一个选择器，3 套皮肤是另一个选择器 | 组合 5 × 3 = 15 种观感；两个维度互不干扰；FR-11.4 的「图案/配色」正好对应这两个选择器 |
| **B** | 皮肤**绑定**配色：切皮肤即切配色，取消独立的主题色选择器 | 3 套皮肤对不上 5 种配色，需要重新定义皮肤集合（例如扩到 5 套皮肤，每套一个图案集 + 一种配色）—— 意味着要新设计 2 套图案 |

**推荐 A**。理由：A 让两项需求同时成立且互不打架；B 会强迫「皮肤数量 = 配色数量」，
而这两件事本来没有必然联系（玩家可能喜欢动物图案但不喜欢玫红）。

> 若选 A，`TileSkin` 仍可携带一个 `preferredPaletteId` 作为「皮肤携带配色」的字面落地 ——
> 首次切到某皮肤时自动套用它的推荐配色，玩家之后仍可单独改。**这属可选增强，见 §9 的 Q1b。**

## 3. 配色方案设计

### K-1 数据模型

```kotlin
// ui/theme/Palette.kt
data class ThemePalette(
    val id: Int,
    @StringRes val nameRes: Int,
    /** 开发者指定的色值；浅色模式下原样用作 primary（见 Q3）。 */
    val seed: Color,
    val light: ColorScheme,
    val dark: ColorScheme,
)

object ThemePalettes {
    const val DEFAULT_ID = 0            // 浅蓝
    val all: List<ThemePalette>
    val default: ThemePalette
    fun byId(id: Int): ThemePalette     // 未注册编号回退默认，与 TileSkins 同构
}
```

`Settings.themeMode: ThemeMode` 换成 `Settings.themePaletteId: Int`（或新枚举，见 Q2）。

### K-2 每套配色如何生成

**核心做法：不只换 primary，而是从 seed 派生出一整套 M3 颜色角色**，且**深色模式另有一套**。
中性色（`background` / `surface` / `onSurface` / `surfaceVariant` / `outline` 等）**沿用现有的中性灰阶**，
不随主题色变化 —— 这是刻意的：若每套主题色都重新定义中性阶，5 套观感的「质感」会变得不受控，
而主题色带来的差异本来就该集中在强调色上。

派生规则（每个角色给出目标，由 K-2 的求解器算出实际色值）：

| 角色 | 浅色主题 | 深色主题 |
|---|---|---|
| `primary` | **= seed 原值** | seed 提亮到在深底上可读 |
| `onPrimary` | 黑或白（按对比度自动选） | 同左 |
| `primaryContainer` | seed 极浅化 | seed 加深 |
| `onPrimaryContainer` | seed 深化 | seed 极浅化 |
| `secondary` | seed 降饱和 | seed 降饱和 + 提亮 |
| `tertiary` | seed **色相 +40°** | 同左 + 提亮 |
| `error` | 沿用现有标准红 | 沿用现有标准红 |

`tertiary` 取色相偏移是为了给「提示高亮」与「连线渐变」一个与主色可区分的强调色
（当前 `PathOverlay` 的渐变正是 primary → tertiary）。

### K-3 用「按对比度求解」而不是「按明度目标硬编码」

派生色的明度不能拍脑袋给定值 —— HSL 的 L 与 WCAG 对比度不是线性关系，
写死 `L = 0.78` 很可能在某个色相上恰好不达标。因此生成器采用**求解**：

```kotlin
/** 在保持色相/饱和度的前提下，二分搜索出满足目标对比度的明度。 */
fun tintMeetingContrast(
    seed: Color,
    background: Color,
    targetRatio: Double,   // 例如 4.5（正文）或 3.0（图形元素）
    preferDarker: Boolean,
): Color
```

**这样对比度是「由构造成立」的，而不是靠事后碰运气。** 事后仍有 `ColorContrastTest`
逐对复核（见 K-5），形成双保险。

**不引入新依赖**：不采用 `material-color-utilities`。理由有二 —— 一是它是基于 HCT 的完整
色调板方案，会产出与 `seed` 不同的 primary（取 tone 40/80），而开发者给的是**确切的色值**，
我们想让它原样出现；二是本项目一直保持依赖精简，而上述求解器只需几十行、且完全可单测。

### K-4 与皮肤的关系（Level 2 的落地）

- **方案 A 下**：`LianLianKanTheme(darkTheme, paletteId, skinId)` 两个维度各自 `CompositionLocalProvider`
  （`LocalTileSkin` 已有，新增 `LocalThemePalette` 或直接由 `MaterialTheme` 的 `colorScheme` 承载 ——
  后者更省事，配色本就走 `MaterialTheme.colorScheme`）。
- **可选的「皮肤携带配色」**：`TileSkin.preferredPaletteId`，见 §9 的 Q1b。

### K-5 对比度测试参数化（本项最大的测试工作量）

`ColorContrastTest` 目前把断言写死在 `LightColors` / `DarkColors` 上。V1.3 需要改为：

```kotlin
for (palette in ThemePalettes.all) {
    assertPairs("${palette.id} 浅色", palette.light, textPairs, MIN_CONTRAST)
    assertPairs("${palette.id} 深色", palette.dark, textPairs, MIN_CONTRAST)
}
```

即 **5 套 × 2 种深浅 = 10 套配色**全部过一遍 WCAG 断言（正文 4.5:1、图形元素 3:1）。
这让「新主题不会踩对比度坑」成为可回归的保证，而不是靠肉眼。

**新增断言（应对 Q3 的撞色问题）**：

- `primary` 与 `error` 在**同一套配色内**必须可区分 —— 对比度不低于 1.5:1，或明度差 ≥ 某阈值。
  红色主题（`#D71418`）下这是最容易出问题的一项：错误反馈的红闪若与选中高亮的红几乎一致，
  玩家就看不出「我点错了」。
- `primary` 与 `tertiary` 必须可区分（提示高亮与选中高亮同时出现时不能混淆）。

### K-6 设置页改动

主题区块由三个文字单选改为**色块选择**：一行 5 个圆形色块，每个填充该主题的 `primary`，
选中态加描边 + 对勾。与皮肤区块形成一致的语言（都是「看得见的选择」）。

需新增字符串：`settings_theme_color`（主题色）与 5 个色名（浅蓝 / 黄绿 / 玫红 / 琥珀 / 正红）。

## 9. 待确认项 —— 已全部确认（2026-09-12）

### Q1：配色与图案的关系 → **方案 A（两个独立选择器）**

主题色（4 选 1）与皮肤（3 选 1）各自独立，组合 12 种观感。

**Q1b → 不做。** 皮肤**不**携带 `preferredPaletteId`，切皮肤不会自动改配色。

### Q2：深浅色的去留 → **Q2-c（替换掉三态，完全取消深色模式）**

**这是本计划中唯一一处「需求降级」，必须如实记录**：`NFR-5.3（深色模式下界面元素对比度可辨）`
与 `FR-13.2（支持浅色 / 深色主题切换）` 将随深色模式一并从 SRS 中删除。
两条要求此前均已实现并通过验收，删除是开发者基于产品定位做出的取舍，**不是实现受阻**。

需要连带处理的实现细节（见 §10）：
- `values-night/themes.xml` 必须处理，否则系统处于深色时窗口底色会与 APP 冲突；
- `isAppearanceLightStatusBars` 不再随主题变化，固定为 `true`。

### Q3：给定 hex 是否原样出现 → **Q3-b（只当种子色，交给标准 M3 色调板算法）**

原 hex **不会字面出现**，产出的是以该色为基调的标准 M3 配色。

**落地方式**：经查证，官方 `material-color-utilities` **未发布到 Maven Central**，
可用的是 `me.tatarka.google.material:material-color-utilities:0.1.2` ——
它是 Google 官方源码的原样转发（已下载 jar 核对：`Hct`、`TonalPalette`、
`SchemeContent`、`SchemeTonalSpot`、`SchemeFidelity`、`DynamicScheme` 等 API 齐全）。
因此**能真正使用标准 M3 算法**，而不是我自己近似。

方案变体选用 **`SchemeContent`**：它保留种子色的色相与彩度（`SchemeTonalSpot` 会把彩度固定为 36，
与给定色值偏离更大）。`SchemeContent` 仍会按 M3 的 tone 取值（浅色下 primary ≈ tone 40），
所以原 hex 不字面出现 —— 这正是 Q3-b 的含义。

**新增风险 R-7**：`material-color-utilities:0.1.2` 是**第三方转发**的官方代码
（作者 Jake Wharton，知名度高，但非 Google 官方发布渠道）。应对：
① 打包进 APK 的体积很小（约 90 KB jar，R8 后更小）；
② 它是纯 JVM、无传递依赖（已核对），供应链面窄；
③ 若日后希望去掉该依赖，`ui/theme/Palette.kt` 是唯一使用点，替换成本可控。

**新增风险 R-8（实施中实测发现）**：**标准 M3 算法不保证强调色之间的色相分离**。

实施配色生成时实测到两件事：

1. **M3 把浅色方案的所有强调色角色都放在 tone 40**，因此 primary / secondary / tertiary / error
   的**亮度完全相同**（两两 WCAG 对比度为 1.00）。它们靠色相与彩度区分，靠亮度是区分不出来的。
2. `SchemeContent` 下 **primary 与 secondary 是同一色相**（仅彩度不同），这是 M3 的刻意设计；
   而**玫红主题（`#FE2472`）的 tertiary 与 error 色相仅差 14.1°**，是 4 套配色里最紧的一对。

**这不是缺陷，而是「M3 只保证与背景的对比，不保证强调色之间的分离」这一事实的体现。**

我一度把「强调色两两色相夹角 ≥ 30°」写成断言，并在失败后把阈值从 30° 调到 20°、再调到 15°；
随后意识到**那条断言测的是一个臆造出来的需求**，调阈值只是在掩盖问题。重新推理后的结论：

- 棋盘上任意一张牌**同一时刻只处于一种状态**，玩家真正要分辨的是「这张牌是不是变色了」，
  即每个强调色**对中性牌底 `surfaceVariant`** 的对比 —— 该断言（≥3:1）**全部通过**；
- 强调色**之间**的色相分离既不是产品需求，也不是 M3 承诺的能力；
- 错误语义由**抖动动画 + Snackbar 文案**承担，颜色只是辅助（选中态另有 1.08 倍缩放，
  与提示态也不只靠颜色区分）。

因此该断言被改为弱形式（只防止角色映射接错导致取到同一个值），并把 14.1° 记为已知限制。
若日后确实需要分离强调色，需在生成后对 `error` 做色相偏转 —— 那会脱离「标准 M3 算法」，
属需要单独决策的改动。

**新增风险 R-9**：`ThemeMode` 的改动面达 **12 个文件 49 处**，其中两处测试断言的正是「三态」定义。
应对：换成 Int 后旧引用无法编译，漏改会在编译期暴露；旧 DataStore 键 `theme_mode` 直接弃用
（用户重选一次主题无成本），不写迁移逻辑。

## 12. 已知观感问题：primary 偏暗（2026-09-12 决定暂不调整）

**现象**：开发者真机查看后反馈 `primary`（主色）偏暗。

**已尝试并回退的方案**：把种子色与白色按 35% 混合以降低彩度（commit `8592158`）。
真机反馈**效果不明显**，已回退（commit `6671161`）。

**根因分析**（记录下来以免重复推导）：`primary` 在本项目里承担两种互相冲突的用途 ——

1. **大面积填充**：Button 底色、主题色块、选中态外发光与描边；
2. **小号文字色**：连击数字、关卡最佳分、「刷新了本关最佳分」、暂停按钮文字。

M3 把浅色方案的 `primary` 固定在 **tone 40**，正是为了让这两种用途同时成立。调整 tone 会同时影响两者：

| primary tone | 配白字（onPrimary） | 配深色字 | 对 `surfaceVariant` | 作为小号文字 |
|---|---|---|---|---|
| 40（当前） | 4.8:1 ✅ | — | 3.5:1 ✅ | 约 4.8:1 ✅ |
| 55 | 3.8:1 ❌ | 约 4.6:1 ✅ | 约 3.3:1（牌底提到 95 时） | **约 3.6:1 ❌** |
| 70 | — | 9.8:1 ✅ | 1.67:1 ❌ | ❌ |

因此「主色变浅」不是调一个数字，而是**拆开一个被复用的颜色角色**：
`primary` 只用于大面积填充，小号文字改用深色的 `onPrimaryContainer`，
同时把牌底 `surfaceVariant` 从 tone 90 提到 95 以维持选中描边的 3:1。

**决定（2026-09-12）**：**暂不调整。** V1.3 维持在 M3 标准的 tone 40 映射。
若日后要处理，按上表执行即可，改动面为 `Palette.kt` + 约 4 个 UI 文件，
且必须同步更新 `ThemePaletteContrastTest`（**调整数值而非放宽阈值**）。
